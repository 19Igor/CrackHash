# Описание 
Распределённая система для взлома хэша под кодовым именем CrackHash, в которой взлом хэша будет производиться незамысловатым перебором всех комбинаций словаря, сгенерированного на основе алфавита (brute-force). Алфавит может состоять только из сточных латинских букв и цифр.
В общих чертах система работает следующим образом:
1. В рамках системы существует менеджер, который принимает от пользователя запрос, содержащий MD-5 хэш некоторого слова, а также его максимальную длину.  
2. Менеджер обрабатывает запрос: генерирует задачи в соответствии с заданным числом воркеров (вычислительных узлов) на перебор слов составленных из переданного им алфавита. После чего отправляет их на исполнение воркерам.
3. Каждый воркер принимает задачу, перебирает слова в заданном диапазоне и вычисляет их хэш. Находит слова у которых хеш совпадает с заданным, и результат работы возвращает менеджеру через очередь.

В рамках однопоточной версии программы реализовано приложение менеджера и воркера, а также организовано простое их взаимодействие через HTTP.
В качестве сериализации использовалась маршализация.
# Требования
- Реализовать на Java 11+ и Spring Boot.
- Использовать Maven
- Развёртывание через Docker-compose, конфигурация с одним воркером.
- Запросы между воркером и менеджером должны гулять по локальной сети по протоколу HTTP, используя в качестве доменов имена сервисов

## Требования к менеджеру
Менеджер должен предоставлять клиенту REST API в формате JSON для взаимодействия с ним. 
Взаимодействие между воркером и менеджером должно быть в формате XML.
Пример json:
```json
{
   "hash":"e2fc714c4727ee9395f324cd2e7f331f",
   "maxLength": 4
}
```
В ответ менеджер должен отдавать клиенту идентификатор запроса, по которому тот сможет обратиться за получением ответа.
Пример ответа:
```json
{

    "requestId":"730a04e6-4de9-41f9-9d5b-53b88b17afac"
}
```


Для того, чтобы менеджер получил результат своего запроса, ему нужно предоставить следующее API:
```
GET /api/hash/status?requestId=730a04e6-4de9-41f9-9d5b-53b88b17afac
```
Тогда в качестве ответа он может получить следующее:
```json
{
  "status":"IN_PROGRESS",
  "data": null
}
```

```json
 {
 "status":"READY",
 "data": ["abcd"]
}
```

Для работы со состояниями запросов используются потокобезопасные коллекции.
Взаимодействие с воркером организовано по протоколу HTTP с помощью Rest Template.
## Требования к воркеру
Взаимодействие между с воркером должно быть в формате XML.

Взаимодействие с менеджером организовать при помощи Rest Template.

Для генерации слов использовалась библиотека combinatoricslib3, которая позволяет генерировать перестановки с повторениями заданной длины на основе заданного множества. Ключевым условием является то, чтобы воркер не держал в памяти все сгенерированные комбинации, так как  при увеличении максимальной длины последовательности их банально станет очень много. Для этого библиотека предоставляет итератор по множеству комбинаций.


# Вторая часть
В рамках второй части была модифицирована система таким образом, что обеспечить гарантированную обработку запросов пользователя( если доступен менеджер), то есть обеспечить отказоустойчивость системы в целом.

Также обязательное условие - это поделить всё пространство слов поровну между всеми воркерами.

## Основные проблемы
Обеспечение сохранности данных при отказе работы менеджера:
- Реализовано хранение информации об обрабатываемых запросах в бд.
- Организовано взаимодействие воркеров с менеджером через RabbitMQ, который после был благополучно запихнут в докер.
Обеспечение частичной отказоустойчивости базы данных:
- Реализовано реплицирование 
- Схема работы: одна primary node и две secondary nodes
- Менеджер отвечает тогда, когда она была сохранена в бд.
Обеспечение сохранности данных при отказе воркеров 
- Должно быть как минимум 2 воркера
- Организовать взаимодействие менеджера с воркерами через очередь (для каждого воркера своя очередь.)
- В случае, когда воркер "сломался" и не отдал ответ, то задача переотправляется другому воркеру, для этого был настроен механизм acknowledgement-ов
- Если на момент создания задач нет доступных воркеров, то сообщение дожидается их появления в очереди, а затем отправляется на исполнителя.
Обеспечение сохранности данных при отказе работы очереди:
- Если менеджер не может отправить задачу в очередь, то он сохраняет её в у себя в бд до того момента, когда очередь станет доступной
- Очередь не должна терять сообщения при рестарте, для этого все сообщения должны быть персистентными (это регулируется при их отправке).
# Как запустить
1. Нужно скачать репозиторий. 
2. Перейти в терминале в корневую папку.
3. Запустить docker-compose с нужной версией программы.
```docker-compose
docker-compose -f docker-compose_mtv.yaml up 
```
или 
```docker-compose
docker-compose -f docker-compose_sv.yaml up
```
